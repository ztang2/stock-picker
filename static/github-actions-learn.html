🤔GitHub Actions 是什么？

GitHub 提供的免费机器人，帮你自动干活。

你告诉它"什么时候做、做什么"，它就在 GitHub 的服务器上自动执行。

类比

👨‍💻 你
写代码、push
→
📋 test.yml
你写的"任务清单"
→
🤖 GitHub 机器人
按清单自动执行
→
✅ 或 ❌
结果告诉你

就像你雇了一个实习生：

  • 你写了一张便签："每次我提交代码，你帮我检查代码能不能跑、Docker能不能build"
  • 实习生（GitHub Actions）照着做
  • 做完了告诉你：通过 ✅ 或者有问题 ❌
  • 这个实习生免费，24小时在线，从不请假

核心概念：CI/CD

CI — 持续集成 (Continuous Integration)

  • 每次push → 自动测试
  • 确保代码没问题
  • 发现bug越早修越便宜
  • 你的stock-picker现在有CI了

CD — 持续部署 (Continuous Deployment)

  • 测试通过 → 自动部署到服务器
  • 用户访问的永远是最新版
  • 需要服务器（AWS/Vercel等）
  • 你以后加AWS时会用到

没有 CI/CD vs 有 CI/CD

❌ 没有 CI/CD

  • 改了代码 push 上去
  • 3天后发现线上崩了
  • 不知道是哪次 push 搞坏的
  • 回滚、debug、浪费2天

✅ 有 CI/CD

  • 改了代码 push 上去
  • 3分钟后 GitHub 告诉你 ❌
  • 马上知道是这次 push 的问题
  • 修一行代码，5分钟搞定

刚才我们就经历了真实的CI/CD流程：

push → ❌ 红色（函数名写错）→ 查log → 改代码 → push → ❌ 红色（另一个函数名错）→ 改 → push → ✅

如果没有CI，你可能永远不知道这些 import 有问题。

📄test.yml — 你的"任务清单"

这是你唯一需要写的文件。放在 .github/workflows/test.yml。

GitHub 会自动扫描这个目录，发现 .yml 文件就注册为一个 workflow。

文件位置

stock-picker/ ├── src/ ├── data/ ├── Dockerfile ├── requirements.txt └── .github/ └── workflows/ └── test.yml ← 这个文件

为什么是 YAML？

YAML 就是一种配置文件格式（像 JSON 但更易读）。GitHub Actions 用 YAML 定义任务。

规则很简单：缩进表示层级，冒号表示键值对，短横线表示列表。

YAML 写法

name: CI
on:
  push:
    branches: [main]
jobs:
  test:
    runs-on: ubuntu-latest

翻译成人话

名字叫 CI
触发条件：
  当 push 时：
    分支是 [main]
任务：
  测试：
    在 ubuntu 最新版上跑

完整文件预览

下一页会逐行详解。先看个全貌：

.github/workflows/test.yml44 行

🔬逐行解读 — 点击每一行看详解

name: CI 👈 点击看详解

给这个 workflow 起个名字。

你在 GitHub Actions 页面看到的就是这个名字。叫什么都行，"CI"是最常见的。

你也可以叫 "Test & Build" 或 "我的自动测试"。

on: push / pull_request 什么时候触发

定义"什么事件会触发这个 workflow"。

push: branches: [main] = 每次 push 到 main 分支时跑

pull_request: branches: [main] = 有人提交 PR 到 main 时跑

其他触发方式：

  • schedule — 定时跑（像 cron）
  • workflow_dispatch — 手动点按钮触发
  • release — 发布新版本时触发
jobs: test: 定义任务

一个 workflow 可以有多个 job（任务）。

我们只有一个叫 "test" 的任务。大公司可能有：

  • test — 跑测试
  • build — 构建 Docker 镜像
  • deploy — 部署到服务器

多个 job 可以并行跑，也可以设置依赖（test 通过了才跑 deploy）。

runs-on: ubuntu-latest 在什么机器上跑

告诉 GitHub "用什么操作系统的机器跑"。

ubuntu-latest = 最新版 Ubuntu Linux（最常用，免费）

GitHub 会分配一台全新的虚拟机给你，跑完就销毁。

其他选项：

  • windows-latest — Windows 机器
  • macos-latest — macOS 机器（跟你的 Mac mini 类似）

💡 免费额度：每月 2000 分钟（Ubuntu），个人项目完全够用。

steps: - uses: actions/checkout@v4 第1步：下载你的代码

steps 是任务里的具体步骤，按顺序执行。

uses: actions/checkout@v4 = 使用 GitHub 官方的 "checkout" 动作

它做的事：把你的 stock-picker 代码从 GitHub 下载到这台虚拟机上。

为什么需要这步？因为虚拟机是全新的，上面什么都没有。需要先把代码拉下来。

uses = 使用别人写好的动作（action）。@v4 = 版本号。

uses: actions/setup-python@v5 第2步：安装 Python 3.11

虚拟机上有 Python 但版本不一定对。这步安装指定版本的 Python 3.11。

with: python-version: "3.11" = 参数：装 3.11 版本。

这跟你的 Dockerfile 里 FROM python:3.11-slim 对应——保持版本一致。

run: pip install -r requirements.txt 第3步：安装 Python 依赖

run = 直接执行命令（跟你在 Terminal 里输一样）。

pip install -r requirements.txt = 装所有依赖。

pip install pytest = 额外装测试框架（以后写更多测试用）。

| 表示多行命令，每行是一条独立命令。

run: python -c "from src.pipeline import ..." 第4步：测试代码能不能导入

这就是"测试"。它做的事：

尝试 import 6 个核心模块。如果任何一个 import 失败（比如文件缺失、函数名错、依赖缺失），整个 workflow 就标红 ❌。

这正是我们刚才遇到的：

第一次：analyze_entry 应该是 analyze_entry_timing → ❌

第二次：compute_quality 应该是 compute_quality_scores → ❌

第三次：全改对了 → ✅

💡 以后可以加更多测试：单元测试、API 测试、数据验证等。

run: docker build -t stock-picker:test . 第5步：测试 Docker 构建

跟你在 Mac 上跑的 docker build 一模一样。

验证 Dockerfile 没问题，所有依赖能正确安装。

GitHub 的虚拟机自带 Docker，不需要额外安装。

如果 Dockerfile 有语法错误或依赖装不上，这步会失败 → ❌。

🔄运行流程 — 从 push 到结果

📝
你在 Mac 上 git push
代码上传到 GitHub
👀
GitHub 检测到 push 事件
扫描 .github/workflows/ 目录，找到 test.yml
🖥️
分配一台全新的 Ubuntu 虚拟机
干净的机器，什么都没装。跑完就销毁。
📥
Step 1: checkout — 下载你的代码
git clone 到虚拟机上
🐍
Step 2: setup-python — 装 Python 3.11
确保版本跟你本地和 Docker 一致
📦
Step 3: pip install — 装所有依赖
FastAPI, pandas, XGBoost... 全部装一遍
🧪
Step 4: import tests — 测试代码
尝试导入 6 个核心模块
🐳
Step 5: docker build — 测试容器构建
按 Dockerfile 构建镜像
📊
报告结果
✅ 全部通过 或 ❌ 某步失败
🗑️
销毁虚拟机
所有数据清除。下次 push 又是一台全新的机器。

关键概念：每次都是全新的机器

这台虚拟机跑完就销毁。不会保留任何状态。

所以每次 push 都要重新：装 Python → 装依赖 → 下载代码 → 跑测试。

（可以用 cache 加速依赖安装，但概念上每次都是从零开始）

你在 Actions 页面看到的

✅ fix: correct all import names in CI test 3m 24s
❌ fix: correct import name in CI test 1m 12s
❌ feat: Docker learning playground + daily updates 1m 08s

每条就是一次 push 触发的 workflow。点进去能看每一步的详细日志。

🐛Debug 实战 — 我们刚才经历的

这不是假设场景，这是你今天真实经历的 CI debug 过程：

第1次 Push → ❌

ImportError: cannot import name 'analyze_entry' from 'src.entry_timing'

问题：函数名写错了。文件里叫 analyze_entry_timing，test.yml 里写了 analyze_entry

修复： 改 test.yml 里的函数名 → push

第2次 Push → ❌

ImportError: cannot import name 'compute_quality' from 'src.quality_scores'

问题：又一个函数名错了。实际叫 compute_quality_scores

修复： 这次把所有函数名都核对了一遍 → push

第3次 Push → ✅

All steps passed!

pipeline OK ✓ risk_manager OK ✓ entry_timing OK ✓ quality_scores OK ✓ early_momentum OK ✓ devils_advocate OK ✓ Docker build OK ✓

常见的 GitHub Actions 用途

跑测试（pytest/jest） 最基本的用途，几乎所有项目都有
代码格式检查（ESLint/Black） 确保代码风格统一
Docker build + push 构建镜像并推到 Docker Hub
部署到 AWS/Vercel/Netlify 测试通过后自动上线
安全漏洞扫描 检查依赖有没有已知漏洞
自动发Release 打tag后自动生成release notes

GitHub Actions vs 其他CI工具

GitHub Actions 跟 GitHub 原生集成，免费，最流行
Jenkins 老牌，需要自己搭服务器，大公司用
CircleCI / Travis CI 第三方CI，被GitHub Actions抢了市场
GitLab CI GitLab自带的CI，用法类似

🧠测验 — 检查理解

答对 0/6

1. GitHub Actions 的 workflow 文件放在哪？

项目根目录的 actions.yml
.github/workflows/ 目录下
GitHub 网页上配置，不需要文件
必须放在 .github/workflows/ 目录下，GitHub 会自动扫描这个目录里的 .yml 文件。

2. runs-on: ubuntu-latest 是什么意思？

在你的 Mac 上跑
在 GitHub 分配的 Ubuntu 虚拟机上跑
在 Docker 容器里跑
GitHub 分配一台全新的 Ubuntu 虚拟机，跑完就销毁。不是你的电脑，也不是 Docker。

3. 什么时候触发 CI？

每天定时跑一次
你手动点按钮时
每次 git push 到 main 分支时
我们配置的是 on: push: branches: [main]，所以每次 push 到 main 就自动跑。也可以配置定时或手动触发。

4. CI 红了（❌）应该怎么做？

删掉 workflow 文件，不用 CI 了
等一天再 push，可能自己好了
查看失败步骤的 log → 找错误 → 修复 → 重新 push
这就是我们刚才做的！看 log 找到 ImportError → 改函数名 → push → 绿了。

5. uses: actions/checkout@v4 做什么？

把你的代码从 GitHub 下载到虚拟机上
检查代码有没有语法错误
把代码部署到服务器
checkout = 把代码拉下来。虚拟机是全新的，上面什么都没有，必须先下载代码才能测试。

6. CI 和 CD 的区别是？

一样的，只是叫法不同
CI = 自动测试（你有了），CD = 自动部署（以后加）
CI 用 GitHub，CD 用 Jenkins
CI (Continuous Integration) = 每次 push 自动跑测试。CD (Continuous Deployment) = 测试通过后自动部署。你现在有 CI，加了 AWS 后就有 CD 了。
